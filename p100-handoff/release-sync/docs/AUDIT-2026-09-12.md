# Numerical audit of the P100 fork — 2026-09-12

Every changed computation in this fork was audited against one standard, set by the owner:

> **bit-identical to upstream, or strictly fewer floating-point roundings. Nothing else
> passes. Reassociation — the same rounding count regrouped — does not pass.**

Scope: the **19 changed compute files** in `f280b2698..HEAD`. The other 84 changed files are
docs, handoff artifacts, harness tools and `tests/test-backend-ops.cpp`.

Method: re-derive each change from the source (not from `OPTLOG.md`, `FINDINGS.md` or the code
comments — several claims in those were later retracted by their own author), then prove it with
a CPU program wherever the domain is enumerable. **No GPU measurement was possible: `/mnt/fast`
was unmounted, so the model file was unavailable.** Everything below is static analysis plus
exhaustive or large-sample CPU proof. The performance figures are quoted from this log's earlier
attempts, not re-measured.

---

## Passes — bit-identical or strictly better

| change | verdict | evidence |
|---|---|---|
| q3_K `__vsubss4` removal | BIT-IDENTICAL | complete per-byte domain, 32/32 exact; the `1/32` rescale is a power of two and commutes with rounding |
| q6_K `__vsubss4` removal | exact unpack | complete per-byte domain 128/128, plus **160,000,000** byte-comparisons over random full words proving the shifts leak no bits across byte lanes. Saturation is **unreachable** in the upstream form, so `__vsubss4` was a plain subtract |
| `VDR_Q6_K_Q8_1_MMVQ` 1→4 | FEWER-ROUNDINGS **and** more accurate | **6.0x** better mean and **15.7x** better tail vs a long-double reference over 4,000,000 random vdr-groups. Peak \|acc\| = 2^18 re-derived independently, inside float's exact-integer range |
| f16 tensor-parallel all-reduce | LOSSLESS (proved), but applied too widely until 2026-09-15 (see below) | **0** probe-admitted-but-lossy cases over all **4,294,967,296** floats; all 1024 predicate/bitwise disagreements are NaN, i.e. conservative. `half→float→half` exact for all 65536 patterns |
| vectorised q6_K dequant | BIT-IDENTICAL (proved) | arithmetic textually identical (`d*sc*(q-32)`, same association), and the index mapping matches over **all 256** superblock outputs, each written exactly once by both kernels |
| fastdiv index replacement | exact inside its guard | **286,286,219** checks over 47 divisors, 0 failures. Guard is tight — first failure is at numerator `2^31+2` (the header comment says `2^31+1`), where fastdiv returns **0** for a true quotient of **2**. All three call sites bound both numerator and divisor |
| `rms_norm` row in registers | BIT-IDENTICAL | same strided ownership and order, same reduction tree, store association textually identical; padding is appended as `+0.0f`, a bitwise no-op because the accumulator sums squares and can never be `-0.0f` |
| binbcast flat fast path | BIT-IDENTICAL | keeps upstream's exact comma-fold over the variadic sources; differs only in an index expression the fast-path predicate (contiguous **and** same shape everywhere) makes equivalent |
| gated delta-net pipelining | BIT-IDENTICAL | `warp_reduce_sum(float2)` is unmodified upstream and applies the same `__shfl_xor_sync` offsets per component; dataflow checked term by term |
| fp16 VKQ fold (the headline fix) | better, but **mislabelled** | it is arithmetically **more** roundings — `+ceil(N/nbatch_fa)` fp32 adds per element, ~4096 at 262144 — not fewer. Nothing is added at lower precision and no term is reordered, so error falls ~`sqrt(N/nbatch_fa)` and it is bit-identical for a single tile. The change is right; the claim should read "+1 fp32 rounding per KV tile, half chain N → nbatch_fa" |
| `nbatch_K = 128` | BIT-IDENTICAL | each accumulator sums strictly ascending `k` with no cross-thread split |
| vec-kernel `half2 VKQ` | dead code, as claimed | `V_DOT2_F32_F16_AVAILABLE` requires `GGML_USE_HIP`; nothing in the tree defines it for CUDA. There is **no** unfixed fp16 accumulation in `fattn-vec.cuh` |

## Failed the standard

### Reverted

**cuBLAS `CUBLAS_GEMM_ALGO3` for wide f16 GEMMs.** A different algorithm is a different
k-accumulation order; both algos run under upstream's `CUBLAS_COMPUTE_16F`, so neither is
nominally more precise and cuBLAS internals are opaque — "fewer roundings" is unprovable in
either direction. Cost of keeping it: perplexity 2.6209 → 2.6214. Gain given up: ~1.8% prefill,
at `ne11 >= 512` only, so decode never touched it. The GEMM call is now byte-identical to
upstream.

### Fixed

**1. The cuBLAS-GEMM attention path was ON by default while its comment said otherwise.**
`ggml_cuda_fa_gemm_enabled()` is `!s || s[0] != '0'` — env unset means enabled — while
`fattn.cu` said *"Off by default — set GGML_CUDA_FA_GEMM=1"*. That is how a default-on
precision regression went unnoticed. Comment corrected.

**2. Mask sequence/head stride ignored — a silent wrong answer.** The softmax kernel applies
`mask->nb[1]` per query row but nothing per head or per sequence, while the sequence loop
advances Q, K, V and dst by `nb[3]`. Upstream offsets the mask by `nb33*(sequence % ne33)`.
With `ns > 1` every sequence would attend through sequence 0's mask. Masked in practice by
`-np 1`. `gemm_supported()` now declines `mask->ne[2] != 1 || mask->ne[3] != 1`, falling back
to the tile kernel.

**3. Missing `scale*0.25` pre-scale of Q (free).** Upstream scales Q down before the fp16
accumulation and scales the fp32 result back up, under a comment naming this hardware:
*"Without the v_dot2_f32_f16 instruction there is a higher risk of numerical overflow in the KQ
calculation."* Both factors are exact powers of two at D=256, so it costs nothing and buys
**64x** of overflow headroom. Without it the fp16 accumulator went non-finite **more often than
the true dot product overflowed** (37 vs 24 per 200k at element RMS 32) — partial sums
overflowing on the way to a representable result — and an inf logit reaches `expf(inf-inf)` =
NaN. Now applied in `fattn_gemm_q_to_f16`, with the softmax multiplying back by 4.
**`alpha` cannot fix this**: cuBLAS applies alpha *after* the accumulation.

**4. Missing `FATTN_KQ_MAX_OFFSET` (free).** Upstream adds 3·ln2 to the running max in tile,
vec **and** mma, capping every probability at 1/8 to give the f16 P buffer and the f16 PV
accumulator 3 bits of headroom. Restored.

**5. q4_0 tile dequant produced ±inf where upstream stays finite (free, and one instruction
cheaper).** The bias was built in fp16 as `offs = __hmul2(dh, -8.0h)`, which overflows for
`|d| >= 8192` and turned **40,584** of the 1,048,576 (nibble, half-scale) cases from a finite
value into ±inf — which NaNs the whole head. The bias is now taken in **integer** (`q - 8`,
exactly representable, range [-8,7]) with a single `__hmul2` by `d`. Verified exhaustively:
**0 value differences from upstream `to_fp16` across the entire finite domain**, and there is
no bias term left to build. Sole residue: `q == 8` with `d < 0` yields `-0.0` where upstream's
`8d + (-8d)` yields `+0.0` — numerically equal, and a KV value of either zero sign contributes
nothing to the attention dot product.

### Open — measured decisions, deliberately not taken by the audit

**6. QK^T accumulates in fp16 (`CUBLAS_COMPUTE_16F`, k=256).** This is the one finding with a
real price. It replaces upstream's **fp32** `KQ_acc` and was justified in-code, three times, by
the claim that "the tile kernel also keeps KQ in half" — which is false. Measured
independently, 200k dot products per row at D=256, upstream modelled with half products plus
fp32 accumulation and the pre-scale:

| element RMS | GEMM (fp16 acc) | upstream (fp32 acc + pre-scale) |
|---|---|---|
| 1 | 9.72e-03 | 2.44e-03 |
| 2 | 1.83e-02 | 2.57e-03 |
| 8 | 1.11e-02 | 1.81e-03 |

**~4x worse mean relative error per attention logit**, and the logit feeds `exp`. The pre-scale
in fix 3 cures the *overflow* but not this: fp16 relative precision is scale-invariant.
`CUBLAS_COMPUTE_32F` was measured at **6.2 vs 14.65 TFLOPS** on this shape; QK^T and PV carry
equal FLOPs and attention is ~86% of long-context prefill, so that is roughly **1.6x on
prefill**. Note also that PV accumulates in fp16 over k = nkv_c (2048) — 32x the chain of the
fork's own tile kernel (nbatch_fa = 64), and the cross-chunk fold is already fp32, so
**shortening nkv_c would reduce that error at little cost.** Both need a measured run.

**Update 2026-09-13 — measured (OPTLOG attempt 152).** QK^T was not the main error: moving it to
fp32 barely changes the op (NMSE 4.1e-5 → 3.9e-5); moving **PV** to fp32 removes the whole gap
(→ 2.3e-6). PV's fp16 error turned out to be mostly a cuBLAS algorithm choice — see "Found after
the audit" below — and is now 3.4x lower at the production batch. At the model level the fp16
path is not distinguishable from fp32 attention: paired per-chunk perplexity, ΔNLL +0.00068
nats/token at both 4096 and 16384 context (t = 1.30 and 1.63), against +0.00031/+0.00035 for the
tile kernel and +0.00052 for a pure fp32 reassociation control. The fp16 default stays;
`GGML_CUDA_FA_GEMM_PREC=32` is the exact option.

**7. `calc_nwarps` 4→2 at `ncols_dst == 1`, and `split_rows` on the multi-column path —
RETRACTED: not worse.** An earlier version of this audit reported these as 1.66x and 1.19x worse.
That came from an unfaithful model: it used 5120 individual float products as leaves, giving
80-term serial chains. The real kernel's leaves are `vec_dot` results that already sum 32 quant
products exactly in integer, and for Q6_K (`QI6_K = 32`, `vdr = 4`, `blocks_per_iter =
4*nwarps`) a 5120-wide row is 20 blocks — so each thread's chain is 3 terms at 2 warps and 2 at
4. Remodelled faithfully and measured on absolute error (immune to near-zero true sums):

| | 20 blocks | 34 blocks |
|---|---|---|
| decode: nwarps=2 / nwarps=4 | **0.978x** | **1.001x** |
| multi-column: split_rows / non-split | **1.025x** | **1.065x** |

Equivalent within noise. An attempted fix (8 accumulators per thread) cost **37.5% of decode**
(`tg256` 19.39 vs 31.04) and was removed. Nothing to fix here; the fork's geometry stands.

### Found after the audit (2026-09-13)

**A data race in the GEMM softmax — silent corruption, in the release.** Since 98de4588f ("alias
P onto S", Sep 1) the softmax wrote the probabilities over the scores it had just read, in one
buffer. On this toolchain the store can land before the load of the same element — with the two
aliased `__restrict__` parameters of the original, with one restrict pointer, and with none. A
probability (≤ 1/8) read back as a score gives exp(4P − m) against a very negative row max:
|ΔP| up to 1.6e7 on the affected rows. Proven by an in-op self-check that runs the kernel twice
on identical inputs: in place 3-6 mismatched launches per ~2240 (fp32, 16k), out of place 0 of
~6700. fp32 perplexity had wandered run to run (3.3144-3.3272 on one 16k chunk); it now repeats
exactly (3.3165 on all 10 runs). fp16 showed no mismatch in 15360 checked launches, but there a
read-back probability overflows half and NaNs the output, and one 4k perplexity run did go NaN.
`test-backend-ops` could never see this: one comparison per case, with a tolerance, on random
data. **Fixed**: P has its own buffer (~1% of the op, 50 MB per GPU at `-ub 2048`).

**cuBLAS `GEMM_DEFAULT` picks a long-chain fp16 kernel for PV at every ubatch ≥ 1024.** Measured
with a standalone harness against an fp64 product of the same fp16 inputs: the COMPUTE_16F
algorithms split into two accuracy families on this P100 — ALGO1-3 (long fp16 chains, NMSE
2.9e-5 at k=2048) and ALGO4-6 (blocked, 2.8e-6) — and DEFAULT switches to the long-chain family
from n = nt·gqa ≈ 6000. ALGO4-6 were never worse at any shape tested (nt 128-2048, k 128-2048).
**Fixed**: PV requests ALGO4 (the most even on speed: ~8% slower than DEFAULT at nt=2048, level
below), with DEFAULT as a fallback. This is not the ALGO3 situation above: there the precision
effect was unmeasured; here it is measured at 10x on the call and 3.4x on the op.

**A lead, not a finding.** Upstream's quantized prefill matmuls on Pascal also run COMPUTE_16F
GEMMs with `CUBLAS_GEMM_DEFAULT_TENSOR_OP`, over far longer sums (5120-17408 terms). Whether the
same family switch applies at those shapes is unmeasured. Separately, upstream's `norm_f32` (in
place) and `group_norm_f32` use the load-then-store-in-a-later-pass pattern that raced here; the
served model uses neither (RMS norm only). **Both leads were followed on 2026-09-14/15 — see the
next section: the matmul one was real and is fixed, the kernel one did not reproduce.**

### Found after the audit (2026-09-14/15)

**A second silent race, in the tensor-parallel peer copies — in the release.** The all-reduce
(`ggml-backend-meta.cpp`, `allreduce_fallback`) lands every exchange in the same per-device
reduction buffer and folds it in with an ADD queued on the destination. Since a4d1103c5 (Aug 31)
the peer copies run on a dedicated copy stream, ordered against the **source** only. A source that
has raced ahead to the next layer can overwrite the destination's reduction buffer before the
destination's ADD of the previous layer has read it, and that ADD sums the wrong partial. The f16
path (e83a7913a) guards this reuse; the uncompressed path — **every decode step, every MTP batch,
every prompt tail under 512 tokens**, and every exchange when the partials are not f16-exact —
never did. Found as sporadic whole-chunk corruption with fp32 matmuls: 3 of 10 unhooked 15-chunk
runs, two NaN and one **silent** (every later chunk off by ~2e-5 NLL, nothing flagged). The
VERIFICATION.md entry "concurrent peer copies: bit-exact, scheduling only" was wrong: scheduling
was exactly what broke. **Fixed**: the copy also waits on the destination's work marker, which
`graph_compute` records after every graph, the ADD included. With a build that delays one device's ADD — which makes
the race certain — the unfixed code corrupts MTP decode (different text, 43.4% draft acceptance
against 78.8%) and the fixed code does not; unforced, the fix ran 6 of 6 clean where the unfixed
code was 3 of 10 bad. It costs 0.7% of tg256 and 0.6% of MTP.

**The prefill-matmul lead, measured: the default is the long-chain kernel, and the slow one.** On
P100 every prefill matmul of a quantized weight is a `COMPUTE_16F` `cublasGemmEx`. At this model's
shapes `CUBLAS_GEMM_DEFAULT_TENSOR_OP` picks the long-chain family (ALGO1-3) from ~256 rows up:
NMSE ≈ 2.2e-8·k against an fp64 product of the same fp16 inputs, 7e-5 to 2e-4. The blocked ALGO6
gives 1.2-1.3e-5 at every shape — **10x** — and at 512 and 1024 rows it is also **faster**:
pp512 240 → 391 t/s (+63%), pp1024 318 → 412 (+30%), pp2048 level. **Changed**: Pascal
`COMPUTE_16F` matmuls request ALGO6, falling back to the default on any failure. Unlike the
reverted ALGO3 this is measured in both directions: 10x on the op, and in paired perplexity
against an all-fp32 run, 4096 × 30 tokens paired per chunk:
upstream's fp16 matmuls +0.00414 nats/token (t 6.7), ALGO6 +0.00343 (t 7.4). ALGO6 minus the
default is -0.00071 (t -1.5) — the right direction, not separable at this sample size; it is kept
for the op-level accuracy and the speed, not for a perplexity claim.

**Where the fp16 path actually loses to fp32, measured.** Same instrument: fp32 matmuls with fp16
GEMM attention sit at **-0.00026 (t -1.4) — indistinguishable from all-fp32** — while fp16 matmuls
with the same attention sit at +0.00343 (t 7.4); paired against each other, +0.00369 (t 8.2). The
measurable distance from fp32 is the matmuls' fp16 inputs and accumulation, not the attention path.
`GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` buys it back (prefill cost in `logs/OPTLOG.md` attempt 153);
`GGML_CUDA_FA_GEMM_PREC=32` does not move the model-level number, though it is 8x at the op level.

**The f16 all-reduce probe assumed a homogeneous model.** The row above proves the per-element
predicate, but it is applied once, to the first eligible exchange; after that every ≥ 512-row
MUL_MAT partial was compressed. A matmul with F32 or BF16 weights, or one requesting
`GGML_PREC_F32` (GLM4, GLM4_MOE and JAIS2 set it on exactly these projections), produces genuine
f32 — rounded to f16 in a model that mixes the two. **Fixed**: eligibility now requires the
matmul's cuBLAS compute type to be F16, per exchange. For Qwen3.8-27B Q6_K every all-reduced projection
(`attn_output`, `ffn_down`, `ssm_out`, `nextn.eh_proj`) is quantized, so no decision, output bit or
speed changes here.

**The same hazard on the same-GPU copy path.** When two virtual devices share one physical GPU
(`GGML_CUDA_DEVICES`), the exchange is a plain `cudaMemcpyAsync` on the *source's* stream rather
than a peer copy — but the destination is still a separate backend with its own stream and the same
reused reduction buffer, so it could be overwritten just as early. **Fixed**: the same wait.
By inspection: no configuration that exercises it produces a trustworthy
number. `GGML_CUDA_DEVICES=3` and `=4` intermittently read `nan` on this model — with the guard on
and with it off, and following the GEMM attention path rather than the copies — while two physical
GPUs are identical run to run. Two physical GPUs never take this branch (`src_physical ==
dst_physical` is false for every exchange), so the guard is inert on everything that ships. The
emulation's own defect is recorded in OPTLOG attempt 153 §8c and left open.

**A disabled slice was zeroed by multiplying it by 0.** Found in the same chase: the all-reduce
zeroes the output of a device whose slice came out empty by scaling it by `0.0f`, under its own
`// FIXME 0.0f * NaN == NaN`. Nothing computed that slice, so the buffer holds whatever the
allocator left there, and a NaN bit pattern survives the "zeroing" into every device's sum.
**Fixed** with `GGML_OP_FILL`, which writes the constant without reading the buffer. On this model
the branch never executes (a verbose run logs it zero times), so this too is a fix on inspection.

**The GEMM running output is now out of place too.** `fattn_gemm_accum_O` loaded and stored the
same device address inside its thread loop — the shape that raced in the softmax. No difference had
been observed; bit-identical after the change (33254 node hashes of a 16k prefill).

**Whole-pass determinism, node by node.** Every graph node's output hashed, 3 prefill runs and 2
MTP decode runs: 0 differences in 33254 and 77324 nodes. The instrument synchronizes per node,
which hides races *between* devices — the peer race above was invisible to it.

**Upstream kernels with the softmax's load/store shape.** In-place `soft_max`, `rms_norm`, `norm`
and `group_norm`, stressed on identical input and compared bit for bit: 0 differing launches in 2100
per in-place case, 2.7e11 element-computations each, at rows too long for the shared-memory cache
path. That bounds the failure rate below the one that was biting (the attention softmax missed 4 of
2240 self-checked launches) rather than clearing the pattern, so nothing upstream is changed on
suspicion.

### Fixed after the audit, verified at runtime

**CUDA-graph replay against a moved q8_1 buffer.** A generation counter bumped on every
reallocation, recorded per captured graph, checked *before* the `cgraph->uid` fast path (which
otherwise returns without comparing anything). Proven at runtime: MTP decode with
`GGML_CUDA_GRAPHS_PRE_VOLTA` on reused captured graphs **61 times** and produced text
**byte-identical** to graphs-off (868 bytes), on a run shown deterministic by an off-vs-off
control. 53.6 t/s on, 53.8 t/s off.

**`np > 1` combine on the fp16 tile path.** `static_assert(np == 1)`. The build compiling proves
every fp16 config row has `np == 1`, confirming the combine that reduces the zeroed `VKQ` was
unreachable; a config that would reach it is now a compile error.

**15-byte over-read.** mmvq staging reads whole 16-byte units past the last block run. 16 bytes of
slack added to quantized tensor allocations on sm_60 and to the q8_1 activation buffer.

**GEMM K/V stride.** `gemm_supported()` now declines `nb[0] != ggml_type_size(type)` — the
condition upstream asserts before the same strided dequantizer (`fattn-common.cuh:1036`).

### Verified clean on inspection

- The q8_1 activation cache cannot serve stale contents: ggml only lets a node overwrite its
  parent's buffer when it is the parent's *last* remaining consumer (`ggml-alloc.c:657`), so every
  matmul that could hit the cache runs before the activation can be mutated.
- The GEMM alloc-size early-out and the dispatch use the same predicate function, so the new
  guards apply to both.
- The vectorised f32↔f16 convert reads and writes exactly `k` elements with the unchanged
  per-element cast, behind a `k % 4 == 0` and 16-byte-alignment gate with a scalar fallback.

### The GEMM accumulator: a precise mode

`GGML_CUDA_FA_GEMM_PREC=32` makes both GEMMs accumulate in fp32 (`CUBLAS_COMPUTE_32F`) over the
same fp16 K and Q, with fp32 scores, probabilities and V. Half×half products need 22 significant
bits, so every product is **exact** — upstream's tile kernel rounds each product to half first.
NMSE against the CPU fp32 reference, at shapes where the GEMM path fires:

| | nb=512 | nb=2048 |
|---|---|---|
| GEMM fp16, release (PV `GEMM_DEFAULT`) | 1.14–1.24e-05 | 3.98–4.25e-05 |
| GEMM fp16, now (PV `ALGO4`) | 1.18–1.29e-05 | 1.20–1.24e-05 |
| **GEMM fp32** | **1.46–1.69e-06** | **1.46–1.70e-06** |
| tile kernel | 2.18–2.43e-06 | 2.26–2.37e-06 |

Flat across kv 4096–65536. Precise mode is **1.4x more accurate than the fp32-accumulating tile
kernel** and 7–26x more accurate than the fp16 default. Cost of precise mode, thermally
controlled A/B: -11.4% pp2048 at depth 16384, -27.2% at depth 65536 (`logs/OPTLOG.md` 151).

## Hazards found (correctness, not rounding) — all closed

- **q8_1 activation cache × CUDA-graph replay** — a captured graph could replay against a freed
  pointer. **Fixed and proven at runtime**; see "Fixed after the audit" above.
- **`np > 1` combine on the FAST_FP16 tile path** — would emit ~1/np of the correct numerator.
  **Closed** with a `static_assert`; the build compiling proves it was unreachable.
- **In-place GEMM softmax racing its own reads** — not a hazard but a live bug, in every build
  since 98de4588f including the release. **Fixed**; see "Found after the audit".

## Documentation errors found in this bundle

- `docs/FINDINGS.md` says the GEMM attention path's PV uses `CUBLAS_COMPUTE_32F` "from caution".
  **Stale** — both GEMMs ship `CUBLAS_COMPUTE_16F`.
- `docs/QUICKSTART.md` recommends `GGML_CUDA_GRAPHS_PRE_VOLTA=1` for MTP. That was exposed to the
  q8_1-cache hazard above until it was fixed; builds from before the fix should not use it. The
  page also does not mention `GGML_CUDA_FA_GEMM` at all — on by default, and the largest numerical
  lever in the fork.
- `CLAUDE.md`'s build command passes `-DP100_NWARPS=8 -DP100_ROWS=4 -DP100_MC_NWARPS=4
  -DP100_MC_ROWS=2`. **None are read any more**; the geometry lives in `mmvq.cu`, gated on
  `__CUDA_ARCH_LIST__ == 600` — so building for any second architecture silently disables the
  whole Pascal geometry block.
