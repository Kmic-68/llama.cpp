    cuda: cuBLAS-GEMM flash attention for pre-Volta long context
    
    On Pascal there are no tensor cores, so long-context prefill falls to
    flash_attn_tile, which measures 3.55 TFLOPS of a 19.05 peak (18.6%) while the
    cuBLAS hgemm beside it in the same model reaches 15.7. Attention is ~86% of
    prefill at 262144 context on qwen3.5 (only ~16 of 65 blocks have a growing KV
    cache), so that gap dominates real long-context use. Attempt 89 established
    that no tile-kernel configuration closes it: 15 configs, stock wins all.
    
    This adds an alternative path that keeps the flash-attention structure (online
    softmax over KV chunks) but issues the two matmuls as cuBLAS GEMMs:
    
        S = K^T Q          strided-batched over the GQA group, f16 compute
        online softmax     mask, running max/sum, P in f16, rescale factor for O
        O += V P           f32 compute -- summing thousands of positive terms in
                           f16 carries several % error
    
    S is computed transposed ([n_kv_chunk x n_tokens], column-major) so one query's
    scores are contiguous: the softmax kernel is then coalesced and PV needs no
    transpose.
    
    Measured at equal thermal state, pp2048 @ d65536:
    
        tile   158.43        GEMM   188.99     (+19.3%)
        tile   183.27        GEMM   200.60     (+9.5%)
    
    Run-to-run variance at depth is large on this machine; call it +10-19%.
    Short context is unaffected -- the path is gated to KV >= 4096, and d=0
    measures 427.05 (off) vs 425.19 (on), within noise.
    
    It also removes the tile path's f16 KV staging. fattn-common converts all of K
    and V on every call; at 262144 that is 512 MiB per GPU, worth ~58k tokens of
    q4_0 KV cache. This path dequantizes one 2048-key chunk at a time, and f16
    caches are read in place via cuBLAS's lda with no copy at all.
    get_alloc_size() gates on exactly the same predicate as the dispatch -- if the
    two ever disagree the kernel writes past the allocation.
    
    Numerics:
    - test-backend-ops -o FLASH_ATTN_EXT: 3949/3949
    - CLAUDE.md gate (c=4096, ppl-orig.txt): 2.6219 +/- 0.01996, inside the
      2.6209 +/- 0.0199 band
    - long-context A/B at c=16384 with q4_0 KV, which is what actually exercises
      the per-chunk dequant: tile 2.6035 +/- 0.02713 vs GEMM 2.6047 +/- 0.02719,
      a 0.04 sigma difference
    
    On by default for cc < VOLTA; GGML_CUDA_FA_GEMM=0 restores upstream behaviour.
    
    Two bugs found during development worth recording, both of which produced
    plausible-looking wrong answers rather than crashes:
    - alpha/beta must match the cuBLAS COMPUTE type, not the data type. Passing
      half* with COMPUTE_32F reinterprets 1.0h as float 2.15e-41, which silently
      degenerates attention into a uniform average of V.
    - the first version wrote f32 scores and read them twice, which at ub=2048 is
      ~400 MB per chunk and made the whole path 16% SLOWER than the tile kernel.
      Unfusing attention pays score-matrix traffic that a fused kernel never does;
      f16 scores plus removing a per-head-group stream sync recovered it.

    cuda: walk gated_delta_net addresses instead of recomputing them
    
    The token loop recomputed q + iq3*sq3 + t*sq2 + iq1*sq1 and three more like it
    every iteration -- twelve 64-bit multiplies per token, and sm_60 has no native
    64-bit multiply, so each expands to an IMAD sequence. That was far more
    instructions than the 16 FMAs of real work in the body. Tokens are visited
    strictly in order, so the addresses form an arithmetic progression and the
    pointers are simply walked. Bit-identical: addressing only.
    
    Measured with test-backend-ops perf, which isolates the kernel from thermal
    drift: head_count=32 1125.30 -> 1113.44 us (-1.1%), head_count=4 171.40 ->
    121.26 us (-29.3%). The gain scales inversely with occupancy -- at low head
    counts per-thread instruction count is exposed, at high counts it hides behind
    warp parallelism.
    
    This model runs in the hidden regime, so its model-level effect is below noise.
    Kept because it is never slower, bit-exact, and a large win for small head
    counts.

    cuda: stage x through shared memory in mul_mat_vec_q (sm_60)
    
    mul_mat_vec_q on Pascal is load-ISSUE bound, not bandwidth bound: measured
    throughput tracks bytes fetched per load instruction, and the card streams
    605 GB/s while this kernel managed 236.
    
    Every ggml block size is 2 mod 4 -- block_q6_K is 210 bytes, block_q8_0 34,
    block_q4_0 18 -- because each block carries a 2-byte ggml_half next to a
    multiple-of-4 payload. Consecutive blocks therefore alternate 4-byte alignment,
    so get_int_b2 must issue two 16-bit loads for every quant word, and the scales
    and block scale cost a load apiece: roughly 7 load instructions and only ~26
    bytes fetched per block.
    
    Have the warp pull its whole contiguous run of blocks in with a few fully
    coalesced 32-bit loads issued from the 4-byte-aligned base below the data, and
    do the per-thread field extraction out of shared memory, where the odd alignment
    costs nothing. The misalignment is preserved in shared memory rather than
    removed, which is what keeps the global side aligned without padding or
    repacking the weights -- a padded block stride was investigated and rejected
    because mmvq and mmq must share a tensor's physical layout.

    runtime bound ptxas emits predicated generic loads (LD.E) for the staging reads
    instead of LDG, which throws away the entire benefit and measured slower than

    cuda: remove __vsubss4 from Q6_K/Q3_K mmvq vec_dot (sm_60)
    
    NVIDIA GPUs have had no SIMD-video hardware since Kepler, so __vsubss4 is emulated
    by ptxas: 9 SASS instructions on sm_60 where a plain subtract is 1. Both mmvq
    K-quant call sites subtract a power-of-two bias from packed sub-byte values whose
    high bits are known zero, which makes the saturation the intrinsic provides
    unnecessary and lets the bias be folded into the extract shifts instead.
    
    For Q6_K, b - 32 is the sign-extension of the 6-bit quant b from bit 5: flipping
    bit 5 and shifting left by 2 puts that sign in bit 7, yielding a packed int8 equal
    to 4*(b - 32) that dp4a consumes directly. Q3_K is the same idea from bit 2 with a
    shift of 5. Both shifts fold into the extract shifts that were needed anyway and
    the bit flip fuses into an adjacent LOP3, so the bias becomes free. The resulting
    power-of-two factor is undone once in the float scale, exactly.
