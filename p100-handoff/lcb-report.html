What was measured, and what wasn't

Scope first, because the headline number does not cover the whole benchmark.

The published Qwen3.8-27B coding figure is LiveCodeBench v6 = 90.3, measured over the full v6 release — 1,055 problems. This run used test6.jsonl, the newest v6 slice: 175 problems from contests between 4 Jan and 6 Apr 2025, 40 tests each, 112 AtCoder (stdin) and 63 LeetCode (functional). That slice skews hard — 80 hard against 43 easy and 52 medium — so it is a tougher set than the published average.

Within it, 60 easy/medium problems were measured at a 32k token budget and 7 hard problems at 64k. The full 1,055-problem benchmark was not run and is not reachable here: at the measured rate it is 3.5–6 days of continuous generation.

Under a 32k budget every hard problem truncated — 5 for 5 — and scored zero. That is not a model result, it is a ceiling: with 46% of the slice rated hard, no configuration could have scored above roughly 54% regardless of how good the model was.

The obvious suspect was a repetition loop, since greedy decoding causes them. It wasn't. A truncated trace was 354 unique sentences out of 355 — coherent combinatorial reasoning that simply had not converged. These problems genuinely want more than 32k tokens, which at ~30 t/s is ~35 minutes each.

Four bugs, one symptom

Every harness defect this run produced output indistinguishable from a model that cannot code.

  1. bwrap --tmpfs /tmp masked the scratch directory

    HumanEval scored 0/3 on provably correct code. The generated solutions were right; the sandbox hid the file they were written to.

  2. --ro-bind / / leaves the root read-only

    bwrap cannot create a mount point at /payload.json on a read-only root, so every LiveCodeBench problem failed inside the judge. Bind targets must land in the tmpfs.

  3. temperature 0

    Chosen for reproducibility; Qwen's documentation forbids it in thinking mode because it causes endless repetition. 5 of 5 hard problems emitted the full budget as reasoning and never answered. Correct sampling is temp 0.6 / top_p 0.95 / top_k 20 — which is also what the published number uses, so the fix improved comparability rather than compromising it.

  4. sys.stdin as a bare StringIO has no .buffer

    Solutions reading via sys.stdin.buffer.read() — standard competitive-programming idiom — crashed, and correct code was scored as failure. Re-judging stored completions moved the sample 82.1% → 85.7% with no regeneration.

The lesson is procedural: validate the judge against a hand-written correct solution (expect 40/40) and a deliberately wrong one (expect 0/40) before trusting any score. Three of these four bugs were found only because a result looked implausible rather than merely bad.

MTP was off — and that's worth more than the benchmark

A 1.51× generation speedup has been sitting unclaimed through the entire optimization campaign.

The GGUF carries a multi-token-prediction head — blk.64.nextn.*, qwen35.nextn_predict_layers — and nothing was using it. It runs on the main model's own weights, with no draft model:

llama.cpp infers MTP only from a draft-repo sidecar or a separate draft GGUF. A head embedded in the main model file is never detected, so it must be requested explicitly — which is why it has been off since day one. The campaign's headline 17.51 → 31.10 t/s was measured entirely without it.

Parallel slots lose here, and CLAUDE.md said so

Four concurrent slots delivered ~6.3 t/s each, ~25 t/s aggregate, against 33 t/s single-slot. Batching amortizes weight reads, which only pays when memory-bound; this workload is documented as compute/issue-bound, measured via core clock scaling. There was nothing to amortize — just the same ALUs split four ways plus per-sequence drafting and four host-side samplers. Reverted.

One caveat on MTP

Outputs are not bit-identical with MTP enabled. Verifying k drafted tokens runs them as a batch of k, taking the batched matmul path rather than mat-vec, and floating-point addition is not associative, so near-ties in the argmax break differently. This is the same non-associativity behind the fp16 accumulator work; it is not evidence of a wrongly accepted token.

Verdict

No evidence of degradation, and the published number is inside the measured interval. Easy problems went 27 for 27. Medium sits at 96.3% once unfinished measurements are set aside. The one genuine solve failure in 60 easy/medium problems is the kind of miss any model of this class produces.

What this run cannot claim: that the full v6 90.3 has been reproduced. It measured 67 problems from the hardest slice of the benchmark, not 1,055 across all of it. The correct reading is that the model and the environment behave like a healthy frontier 27B on the tiers where the sample is large enough to say anything, and nothing anywhere in the run pointed at the kernels.
